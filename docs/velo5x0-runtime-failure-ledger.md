## Management Access Loss

Read-only investigation on 2026-10-08 proved that GE1 itself remains alive:
enp0s20f2 retains 192.168.88.254/24, carrier is up, it has no XDP attachment,
and an interface-bound ping to its actual Windows peer passed 2/2. VPP,
the control API, Nginx and Kea are active. This management loss is not a
GE1 driver failure or a stopped Web service.

The DHCP journal provides the configuration transition. At 21:48:14 +08:00,
Kea listened on enp0s20f2 and issued the factory management lease. At
21:48:30 +08:00, its replacement configuration listened only on
lylan-enp0s20f3, with the GE2 business pool and router 192.168.88.66.
The current file still contains no management listener or management subnet.
`currentDHCPServers` includes only saved business `dhcp_server` resources;
`RenderKeaDHCP4Config` renders them as the entire /etc/kea/kea-dhcp4.conf.
This overwrites the management DHCP generated by firstboot instead of
preserving it. Protecting the management physical interface from VPP does
not protect its shared service configuration.

Packet observations corrected the earlier Windows adapter assumption.
GE1 is connected to Windows interface 4, MAC 00:e0:4c:68:00:7b, which now
has only 169.254.171.157. Windows interface 13, MAC 00:e0:4c:68:02:10,
is on GE2 and holds 192.168.88.120 from DHCP server 192.168.88.66.
Its ARP for 192.168.88.254 fails, while GE2 ICMP passes 3/3 and HTTPS on
192.168.88.66 returns 200. The GE2 result is not management-GE1 acceptance.

A second, independently observed defect is overlapping connected prefixes:
GE1 management and the GE2 LCP both install 192.168.88.0/24. The live
route lookup for a reply from 192.168.88.254 to 192.168.88.120 selects
lylan-enp0s20f3, not GE1. Restoring DHCP alone is insufficient to establish
management recovery without also resolving or explicitly isolating these
independent same-subnet paths.

The subsequent management repair keeps the user's addresses unchanged.
Kea 2.2 rejects duplicate subnet prefixes even with explicit interface
bindings, so management DHCP now has its own service, configuration, PID
directory and lease database. Business applies still own only the original
Kea service/file. Firstboot preserves the business file, excludes its pools
from management allocation, and migrates only a legacy management-only file.
New gateway images enable both services and start business DHCP without a
factory management subnet.

Management source replies use a persistent networkd rule/table 19088 bound
to GE1. Management DHCP option 121 installs an on-link /32 route to .254
on the client's management NIC, avoiding the two competing Windows /24
routes without changing GE2. The actual PC now holds .88.100 from .254 on
GE1 and .88.120 from .66 on GE2.

Eleven management regressions, eighteen hardware regressions, environment
migration and the targeted source gate passed. Fresh sealed helper, unit
and firstboot artifacts were deployed through hotfix-deploy, with source
fingerprint 1a84fca16e80a6902650b4a8f9d726b957d87eefe155f5d2624ee177a21cbadd.
The original configuration/database backup is
/var/lib/ly-route/management-repair-backup-20261008T154223Z.
An authenticated public runtime apply committed, both NICs renewed DHCP,
and management remained accessible. Networkd reconfiguration and management
DHCP restart also preserved access: unbound PC ping passed 4/4 and HTTPS on
.254 returned 200. Failed systemd units are zero; WAN remains DHCP_BOUND.
Service enablement and boot configuration are persisted, but a physical
reboot was not performed in this repair. GE2 business Internet acceptance
is separate from these management checks.

## AF_XDP Lifecycle

2048-byte data buffers were insufficient for this igb zero-copy RX path.
3072-byte buffers allowed real DHCP reception. Duplicate creation previously
detached existing XDP; patch 0007 rejects the duplicate before cleanup.
Patch 0008 tracks RX ownership through fill-ring consumption and RX dequeue.
Two real GE2 create/delete cycles returned about 2048 buffers each, without
the earlier per-cycle leak. Duplicate SFP1 creation was rejected while its
XDP program remained attached and VPP public ICMP passed 3/3.

The first local patch-build verification was invalid: git apply inside an
ignored non-repository source subdirectory could skip the patch. The fresh
build was repeated with explicit patch-root application and content checks.
Only the rebuilt plugin with SHA-256
1f07a0c7658378bcd6483ab4fc14a58f6896c55b3b7543351591b41e76b13c90
provided the successful lifecycle observations above.

## GE2 DHCP Blockers

GE2 has the user's saved 192.168.88.66/24 LAN address. LAN1 has only a role
label, not a business address. Including that label in the native-path request
locked unrelated GE2 application. Role-only selection no longer requests a
forwarding attachment; the saved LAN1 role is preserved.

No DHCP server existed. A GE2 server was saved through the public API with
192.168.88.120-192.168.88.199, router 192.168.88.66 and a 43200-second lease.
The real apply then failed at LCP creation and rolled back. Direct reproduction
reported "linux-cp pair creation failed (-11)"; VPP logs showed that
/dev/vhost-net was absent. The installed kernel config has VHOST_NET disabled,
and modprobe vhost_net confirmed that the module does not exist.

The owning kernel fragment and package-module checks now require VHOST_NET,
VHOST, VHOST_IOTLB and built-in VHOST_TASK. Startup loads tun/vhost_net.
This requires a new kernel boot; existing-kernel GE2 DHCP and independent-PC
Internet acceptance are not passed. GE2's LAN subnet also overlaps GE1
management; retain the user's address pending an explicit topology change.
The new kernel release is 6.18.54-velo5x0-r2, with a separate package and
module directory so an update does not overwrite the running kernel.

The verified CI kernel package was installed through the sealed deployment
path. The first reboot selected the still-inserted old installer USB; installation
was interrupted at disk selection without formatting. After the user removed
the USB and rebooted, the installed r2 kernel booted successfully. Board, VPP,
control API and Kea are active; modprobe vhost_net succeeds and /dev/vhost-net
exists. The old kernel and pre-reboot configuration/database backup remain.

The public GE2 apply then committed and created its VPP/LCP address and Kea
binding. Live readback exposed another owning-layer omission: typed interface
application discarded the DHCP commands from AddressAssignments, and the WAN
NAT flag never produced an ordinary LAN/WAN NAT operation. DHCP assignments now
have a supplemental interface owner with exact client readback and idempotent
lease preservation. Explicit DHCP-owned IPv4 is excluded from static-address
drift repair. WAN NAT now has a route owner that verifies inside/outside roles
and interface-address tracking; retired WANs preserve only shared inside roles.
The fresh controller was deployed, and the real public apply committed again.
SFP1 is DHCP_BOUND at 192.168.1.221/24, the NAT pool contains that address,
GE2 is the NAT inside, and VPP public ICMP passed 3/3.

An earlier independent GE2 client acceptance failed. The router's external PHY
reported no carrier and zero receive packets, while Windows interface 18 reported
1 Gbps and retained APIPA. DHCP renewal timed out. Removing the GE2 AF_XDP/LCP
temporarily did not restore carrier, so the timing correlation does not prove
AF_XDP is the cause. Temporary negotiation tests were restored to the original
automatic 10/100/1000 advertisement. GE2 port/cable mapping and PHY negotiation
were still under investigation at that point; no Linux forwarding substitute was introduced.
Subsequent GE2 client verification has working carrier, DHCP and HTTPS.
The separate DNS failure and Wi-Fi business acceptance are documented in
velo5x0-ge2-wifi-repair.md.
